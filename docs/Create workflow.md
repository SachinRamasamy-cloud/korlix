Korlix Workflow Inspector — Phase 1 Product and Problem Specification

Document status: Implementation baselinePhase: Phase 1 — Korlix-native workflow inspectionAudience: Compiler engineers, runtime engineers, frontend engineers, QA engineers, product ownersLast updated: 2026-08-01

1. Executive decision

Korlix Workflow Inspector Phase 1 will be a compiler-integrated workflow analysis and runtime inspection system for Korlix projects.

It will not infer the primary workflow by sending source code to an AI model. Instead, it will:

Read the semantically resolved Korlix program.

Extract possible execution paths into a language-independent Workflow IR.

Validate those paths using deterministic graph rules.

Instrument generated code during development.

record the path that actually executed.

Overlay static and runtime information in an interactive inspector.

Use AI only to explain validated findings or suggest corrections.

The product promise is:

Korlix shows developers what workflow their code defines, what path actually executed, and where the implementation contains incomplete, unreachable, unsafe, or unresolved behavior.

2. Problem definition

2.1 Primary problem

AI-assisted and vibe-coded applications can appear correct at the file or component level while the complete user workflow is incorrect.

Typical failures include:

A button calls the wrong handler.

A success branch exists but the failure branch is missing.

Loading state is enabled and never reset on one path.

A route exists but cannot be reached.

An API request fails without visible feedback.

A retry loop has no termination bound.

A background task is started but never awaited, cancelled, or classified as detached.

A state update occurs after navigation or component disposal.

A destructive operation is reachable without confirmation.

AI review explains individual files but misses cross-file execution order.

The underlying issue is that most review tools operate on source text, diffs, or isolated functions. They do not present the developer with a reliable end-to-end execution model.

4. Phase 1 goals

G-01 — Deterministic workflow extraction

Given the same resolved Korlix program, the inspector must produce the same canonical workflow graph.

G-02 — Human-readable workflow visualization

The graph must communicate application behavior using product-level concepts such as:

Page load

Button click

Validation

State change

API request

Success

Failure

Navigation

Retry

Parallel work

Completion

It must not expose low-level compiler blocks as the default user experience.

G-03 — Exact source traceability

Every source-backed graph node and diagnostic must link to its exact .klx source range.

G-04 — Deterministic validation

The validator must identify structural workflow defects without requiring AI.

G-05 — Runtime execution overlay

During development, the graph must show:

Executed nodes

Unexecuted nodes

Failed nodes

Active nodes

Duration

Runtime parent-child relationships

Orphaned runtime events

G-06 — Safe-by-default telemetry

Runtime collection must be local by default and must not collect secrets, credentials, raw request bodies, or personal data unless an explicit future opt-in design permits it.

G-07 — CI-compatible output

The same findings shown in the UI must be exportable as machine-readable JSON and SARIF.

G-08 — Stable foundation for Phase 2

The Workflow IR, runtime event protocol, validation engine, and UI must not depend on Korlix-only AST structures. Phase 2 adapters for React, JavaScript, Python, and other ecosystems must be able to emit the same IR.

5. Non-goals

Phase 1 will not include:

React, Next.js, Vue, Svelte, Python, FastAPI, Django, Rust, Go, or Java adapters.

Full formal verification of arbitrary programs.

Production observability or long-term trace storage.

Cloud collaboration.

Automatic rewriting of application source.

AI-generated primary workflow graphs.

Capture of request or response payload values.

Complete resolution of runtime-generated routes or code.

Process mining over historical production event logs.

Cross-service distributed tracing outside a Korlix-native application.

These exclusions prevent Phase 1 from becoming an unbounded observability platform.

6. How Korlix solves the problem

6.1 Static workflow model

Korlix already parses, resolves, validates, and generates code. Phase 1 adds a workflow lowering pass after semantic resolution.

Korlix source
    ↓
Parser
    ↓
Resolved and typed semantic representation
    ↓
Workflow lowering
    ↓
Normalized Workflow IR
    ↓
Validator + Inspector + Instrumentation plan

The static graph answers:

What can happen?

What triggers each operation?

Which branches are possible?

Which failures are handled?

Which state changes occur?

Which terminal outcomes exist?

Which nodes are unreachable?

Which targets are unresolved?

6.2 Runtime execution model

Generated development code receives semantics-preserving instrumentation.

Static workflow node ID
    ↓
Instrumented generated operation
    ↓
Runtime start / completion / failure events
    ↓
Local collector
    ↓
Static graph overlay

The runtime view answers:

What did happen?

In what causal order?

Which branch executed?

Where did execution fail?

Which static nodes were not exercised?

How long did each observed operation take?

6.3 Deterministic validation

The validator evaluates explicit graph properties, including:

Entry and terminal reachability

Missing branches

Unhandled failure paths

Unbounded retries

Unsafe redirect cycles

Unjoined async work

Loading state left active

Orphaned state writes

Invalid source spans

Runtime events that do not map to static nodes

6.4 AI explanation layer

AI is downstream of deterministic evidence.

Input to AI:

Workflow subgraph

Source locations

Runtime evidence

Rule IDs

Confidence and unresolved markers

Expected AI role:

Explain why a finding matters.

Summarize the user-visible consequence.

Suggest a correction.

Generate a test candidate.

AI must not silently add missing graph nodes or convert uncertain targets into confirmed behavior.

7. Product workflow

7.1 Developer starts the inspector

korlix dev --workflow

Expected output:

Application:         http://localhost:3000
Workflow Inspector: http://localhost:3001

Static analysis:
  Workflows: 14
  Nodes: 138
  Errors: 1
  Warnings: 4

7.2 Developer selects a workflow

Example workflow:

Checkout
  Start
    → Pay clicked
    → Validate order
    → Loading = true
    → POST /orders
        ├─ success → Navigate /success
        └─ failure → Show order error
    → Loading = false
    → Complete

7.3 Developer runs the application

Observed overlay:

Pay clicked          completed
Validate order       completed
Loading = true       completed
POST /orders         failed: HTTP 500
Show order error     completed
Loading = false      completed
Navigate /success    not executed

The inspector must distinguish:

Not executed: available path not covered by this run.

Failed: execution entered the node and completed with failure.

Unresolved: static analysis could not establish the target.

Invalid: graph or runtime event violates a required property.

9. Quality attributes

9.1 Correctness

Same semantic input produces the same canonical graph.

Graph transformations are deterministic and idempotent.

Instrumentation does not change program behavior.

Uncertainty is represented explicitly.

9.2 Performance

9.3 Security

Collector binds to loopback by default.

No cloud export by default.

Sensitive fields are recursively redacted.

Payload size and nesting depth are bounded.

Runtime protocol rejects malformed or oversized events.

File paths are project-relative in exported data unless explicitly configured.

9.4 Compatibility

Workflow IR includes a schema version.

Optional unknown fields can be ignored safely.

Unsupported required node types cause an explicit compatibility error.

Migrations preserve semantic graph identity where possible.

9.5 Explainability

Every finding must expose:

Stable rule ID

Severity

Human-readable message

Source location

Affected graph node

Evidence

Suggested remediation category

10. Success criteria

Phase 1 is accepted when:

The approved Korlix semantic fixture corpus produces reviewed canonical graphs.

Every required graph property is covered by automated tests.

Runtime instrumentation passes differential behavior tests.

Known secret fixtures produce zero telemetry leakage.

The inspector shows static and runtime states without conflating them.

Source navigation works for every source-backed node.

The CLI fails correctly on configured error severity.

SARIF output validates against the target schema.

Incremental extraction preserves unaffected node IDs.

The architecture exposes a documented adapter boundary for Phase 2.
